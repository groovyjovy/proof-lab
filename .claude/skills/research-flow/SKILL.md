# 研究の進め方(proof-lab)

この研究の目的は、状態機械と形式証明の力を知ること。機能は、その力に負荷をかけるための手段で、CRUD のような単純な機能は足さない。アプリの堅牢さを示す道具(証明、モデル検査、lint、テスト)は手を抜かず、応急処置で済ませない。目的と経緯は goal.md、日々の決まりは CLAUDE.md にある。

この進め方は、事例研究1〜3で実際にたどった流れを書き留めたもの。手順を飛ばしたときに何が起きたかも、理由として添えてある。

## 1. 事例研究の流れ

事例研究は「黙って置いている前提を1つ崩す」もの。崩れた前提に、どの定理やテストが寄りかかっていたかが分かるのが、研究としての収穫になる。

1. **崩す前提を決める。** goal.md の Phase 5 の「次の候補」から選び、何の前提が崩れるかを一文で書く(例: 「飛んでいる副作用は高々1つ」「サーバーの行が変わるのは自分の更新だけ」)。
2. **性質を先に書く。** goal.md の4章に P 番号で足す。後から書くと、実装に合わせた性質になる。
3. **Lean で仕様を書く**(`spec/Spec/App.lean`、認可なら `Authz.lean`)。TypeScript はまだ書かない。
4. **証明を通す**(`AppProofs.lean`・`AuthzProofs.lean`)。`lake build` は警告をエラーにしているので、`sorry` が残ると通らない。
   - 通らないときは、まず定理の書き間違いか設計の穴を疑う。P10 の定理の誤り、知らせで応答待ちを抜けてはいけないこと(P11・P14)は、どちらも証明が通らないことで見つかった。
   - 環境(サーバー)について仮定したことは、`Server` の前提として書き出す(`ok`・`applied`)。書き出した前提は、そのままサーバーの作りへの要求になる。それを確かめる性質テストも書く(事例研究3の `NoticeOk` は、DB のトリガーをいつ知らせるかを決めた)。
5. **窓口の JSON を足す**(`spec/Main.lean`)。形は TypeScript の型と同じにし、手で書く。
6. **TypeScript に写す**(`machine.ts`、副作用は `effects.ts`、実行は `app.svelte.ts`)。lint の決まりは理由があって置いている。`$state` は `app.svelte.ts` だけ、`fetch`・`setTimeout` は `effects.ts` だけ、DB は `src/lib/server/authz/` だけ、画面の操作は `#lib/ui` の Action 部品だけ。lint に止められたら、決まりを外すのではなく置き場所を考え直す(事例研究2で、画面に `$state` を置こうとして止められ、地図の子の部品にした)。
7. **突き合わせ**(`tests/conformance/`)。
   - `exhaustive.test.ts` の `branches` に、新しい操作・応答・知らせをすべて足す。状態の数の期待値は、テストが教える数に直す。
   - `app.test.ts` の生成器に足し、新しい場面に届いたかの確認(`reached`)も足す。決まった種で全部の場面に届くことを確かめる(届かなければ、生成器に決まった手順の塊を足す)。
8. **モデル3**(`model/model3-app.ts`・`model3-app.test.ts`)。
   - 範囲(作成・編集・検索)に環境の動きを足す。応答や知らせは「出す」と「届く」を分け、届く途中のものは並べ替えて数える。
   - 性質と、探索が狙った場面に届いたかの確認を足す。
   - よくある素朴な実装を、`Machine` を差し替えた「壊した版」として足し、最短の反例の手順をテストに書く。予想と違う反例が出たら、それは発見なので記録する(事例研究3では、自分の更新が戻ってくる知らせではなく、もう読み込んだ変更の遅れた知らせが反例だった)。
   - メモリ(4GB)が尽きたら、範囲を分ける・並べ替えて数える・上限を置く。状態が無限にないか(ログアウト失敗のたびに番号が増える、など)も疑う。
9. **サーバー**(マイグレーション、`src/lib/server/authz/`)。性質テスト(`tests/properties/`)の期待値は、Lean の判断表(`rules.ts` の `decision`)から引き、テストの中で認可を書き直さない。
10. **E2E**(`tests/e2e/`)。決まった手順で、`page.route` で通信を止めたり返したりして状況を作る。
11. **画面の記録**。`scripts/drive.ts` にシナリオを足し、`pnpm drive --scenario <名前> --screenshot` で撮る。tour(全状態)も流す。
12. **わざと壊した版で赤を確かめる**(2章)。
13. **記録する**(`references/checklist.md` の一覧を上から順に)。
14. **合否を確かめ、探索する**。`pnpm test`・`pnpm lint`・`pnpm check`・`pnpm build` を通し、フェーズの区切りとして `pnpm explore 3m` を流す。探索の報告(破れた性質、届かなかった場面)を記録する。
15. **commit して push する**(事例研究の区切りごと。push は `foundation` ブランチ)。
16. **報告する**(`references/report.md` の形)。

## 2. わざと壊した版

「テストが通った」だけでは、そのテストが本当に見張っているかは分からない。性質ごとに、その性質だけを破る版を作り、どの層のテストが赤になるかを確かめて記録する。この表(どの層が何を見つけたか)が研究の中心的な記録になる。

- **モデル3の壊した版**は、テストとして残す(`Machine` の差し替え。毎回流れる)。
- **画面・サーバーの壊した版**は、実装を一時的に書き換えて流し、終わったら元に戻す。戻す前に退避を取り、戻したら `cmp` で同じかを確かめる。
- 壊した版でテストが赤にならなかったら、テストの手順を疑う。事例研究2の E2E は、最初の手順では「番号をセッションごとに振る版」を見逃した。モデル3の反例の手順を読んで、番号が重なる手順に直した。
- 壊した版がどの性質も破らなかったら、それも結果として記録する(事例研究3の「本人を見ない版」)。空振りでないこと(その場面に届いていること)は、数えて添える。

## 3. 見つけたものの扱い

探索(`pnpm explore`)、E2E の失敗、手での確かめ、利用者の報告のどこで見つけても、直す前に次の順で扱う。

1. **再現する。** 性質テストなら、表示された種で同じ入力を流す(`SEED=<種> pnpm test <ファイル>`)。本物の画面の探索は再現できないので、`evidence/explore/` の記録(トレース、スクリーンショット、`proxy.json`)を読む。
2. **決まった入力のテストにして、赤を確かめる。** E2E、単体テスト、モデル3の対照のどれか、いちばん小さく決定的に書けるもので書く。
3. **直して、緑を確かめる。**
4. **モデルの前提が間違っていたなら、モデルに取り込む。** 世界がモデルと違う振る舞いをした(保存はタイムアウトしてもコミットされていた、地図は状態機械の外でタイルを取りに行く、知らせと読み込みの応答は順番が入れ替わる)なら、Lean の環境の応答やモデル3の環境の動きに足して、以後は証明と全探索で毎回確かめる。
5. **記録する。** どこで見つけ、どの層で止めたか。

手で確かめたことは一度きりで、次の変更では誰も見ていない。テストにしないなら、その理由(本番の動きに関わらない、など)を書いておく。事例研究3では、手で数えて見つけた隙間を直しただけでテストを書かず、利用者の指摘で単体テストにした。

## 4. 報告

完了報告には、CLAUDE.md の決まり(テストの結果・スクリーンショット・壊した版の赤)を添える。測った数には【測定】を付け、確かめていないことを確かめたように書かない。報告の形は `references/report.md` にある。
