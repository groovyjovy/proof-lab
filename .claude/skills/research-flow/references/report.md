# 事例研究の報告の形

日本語で、結論から書く。測った数には【測定】を付ける。確かめていないことは、確かめていないと書く。

```markdown
事例研究N「〜」を終え、commit して push しました(`<commit>`)。`pnpm test` は X ファイル・Y 件がすべて通り、lint・型チェック・ビルドも通っています。

## 足した機能
(何ができるようになったか。2〜4行。機能そのものが目的ではないことに触れてもよい)

## 証明が要求したこと
- (通らなかった定理と、それで変えた設計)
- (書き出した前提と、それがサーバーの作りに求めたこと)

## どの層が何を見つけたか(わざと壊した版)
| 壊した版 | Lean | モデル3 | 性質テスト | E2E | Bombadil |
|---|---|---|---|---|---|
| … | | 反例(N手) | | 赤 | |
| (破れなかった版) | | 破れず(状態数、空振りでない根拠) | | | |

(`machine.ts` を書き換えた版で突き合わせが赤になるのは当然なので、表には入れない。Lean の列は、壊した設計を仕様に書いたときだけ埋まる)

(予想と違った反例があれば、何を予想していて、何が出たか)

## 確かめた結果【測定】
- Lean: 性質の定理 N 個、標準の公理だけ(テストで確認)
- モデル3: 範囲ごとの状態数と、成り立った性質
- 突き合わせ: 状態 × イベント = 通り。ランダムは決まった種で全場面に届いた
- 性質テスト・E2E の件数
- `pnpm explore 3m`: 破れた性質、届かなかった場面、探索で見えた機能の効果
- スクリーンショット: `evidence/.../README.md`

## お伝えしておくこと
- (変えた既存のテストと、その理由)
- (探索で届かなかった場面と、どこで代わりに確かめているか)
- (途中で見つけて直したこと。テストにしたか)

## 証明の外に残っているもの
- (単体テストだけ・性質テストだけで確かめているもの)

次は〜(崩す前提を一文で)。
```

## 書き方の注意

- 「できました」には、テストの結果・スクリーンショット・壊した版の赤のどれかを添える(CLAUDE.md)
- 手で一度だけ確かめたことは、そう書く。テストにしていなければ、それも書く
- 数は、そのときに測ったものを書く。前の回の数を使い回さない
