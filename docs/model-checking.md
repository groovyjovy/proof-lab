## モデル2: 権限剥奪(P3)

### モデル

goal.md 5章のとおり、DB 上の role(`serverRole`)と Cookie cache 上の role(`cachedRole`)を別の状態として持つ。

- 登場するのは a-staff 1人と管理者だけ(バグが出る最小規模)
- a-staff: 読み込む → 編集する → 保存を送る → サーバーが受理 / 拒否(拒否されたら読み直す)
- 管理者: a-staff の編集権限を剥奪する(1回)
- Cookie cache: いつでも DB の値に追いつきうる(`maxAge` 切れの再取得を、いつ起きてもよいとして表す)
- 保存リクエストには、送った時点の Cookie の role と「剥奪の後に送ったか」(`afterRevoke`)を載せる
- P3 は「`afterRevoke` が真の保存が、一つもコミットされていない」という不変条件にした

設計の違いは、サーバーが保存を受理するときに見る role の出どころだけ(`cache` か `db` か)。

### 反例(cache で認可)

自作検査器の出力【測定】:

```
初期状態
→ a-staffが読み込む
→ a-staffが編集する
→ 管理者が剥奪する
→ a-staffが保存を送る(Cookieのrole=editor)
→ サーバーがcacheのrole=editorで保存を受理する
```

TLC の出力(抜粋)【測定】:

```
Error: Invariant P3 is violated.
State 1: <Initial predicate>
State 2: <Load ...>
State 3: <Edit ...>
State 4: <Revoke ...>     serverRole = "none", cachedRole = "editor"
State 5: <Send ...>       inflight = <<[cookieRole |-> "editor", afterRevoke |-> TRUE]>>
State 6: <Accept ...>     committed = <<TRUE>>
```

剥奪されたあとでも、Cookie cache が更新されるまでは保存が通る。goal.md の予想どおり。

### 自作検査器と TLC の突き合わせ

| | 自作検査器 | TLC | |
|---|---|---|---|
| cache: 反例の長さ | 6 状態 | 6 状態 | 一致。どちらも幅優先なので最短の反例 |
| cache: 反例の手順 | 読込→編集→剥奪→送信→受理 | Load→Edit→Revoke→Send→Accept | 一致 |
| cache: 全状態数 | 20(不変条件なしで全探索) | 20(`-continue`) | 一致 |
| db: 全状態数 | 18 | 18 | 一致 |

すべて【測定】。

反例を見つけて止まった時点の状態数は、自作検査器が 19、TLC が 16 で違う。
自作検査器はキューから取り出すときに、TLC は状態を生成したときに検査するので、止まる位置がずれる。
全状態数で比べると一致するので、二つは同じ状態空間を探索していると判断した。

### テストがずれを捕まえることの確認

複製したプロジェクトで TS 版だけを「常に DB で認可する」(`const role = s.serverRole;`)に書き換えると、
`モデル2 cacheで認可` と `TLA+ Revocation cache` の 2 件が失敗した【測定】。
TS 版と TLA+ 版の片方だけを変えると、テストが落ちる。
これは一度だけ手で回した確認で、テストには含めていない。

## DrawUI: 保存中はいつか必ず終わる(L1)

### モデル

付録Bの `next` と同じ遷移に、保存リクエストの通信路を足した。点の座標は L1 に関係しないので、点の数(0〜3)だけを持つ。

- 通信路: 応答待ち(`inflight`)の応答は、成功・失敗のどちらかで返るか、失われる(`lost`)
- タイムアウト(定数 `HasTimeout` が真のときだけ): 保存中なら描画中に戻す。遅れて届く応答は捨てる

公平性の仮定(これがないと活性の結果に意味がない):

| 対象 | 仮定 | 理由 |
|---|---|---|
| サーバーの応答 | WF: 応答待ちが続くなら、いつか応答する | 応答が来ない場合は「失われた」で別に表している |
| タイマー | WF: 保存中が続くなら、いつか発火する | 実装ではタイマーが必ず発火する |
| ユーザーの操作 | 仮定しない | 何もしないこともありうる |
| 応答の喪失 | 仮定しない | 起きることも起きないこともある |

### 結果

タイムアウトなし(付録Bのまま)の TLC 出力【測定】:

```
Error: Temporal properties were violated.
State 1: <Initial predicate>  kind = "view"
State 2: <Start ...>          kind = "drawing"
State 3〜5: <AddPoint ...>    points = 1, 2, 3
State 6: <Commit ...>         kind = "saving", net = "inflight"
State 7: <Lose ...>           kind = "saving", net = "lost"
State 8: Stuttering
```

確定して保存中になったあと応答が失われると、そのまま保存中から抜けない。goal.md の付録Bに書いた既知の課題が、反例として出た。
タイムアウトありでは、7 状態すべてで L1 が成り立った【測定】。

### 合格が空虚でないことの確認

仮定を一つずつ外した変種でも回した【測定】。
`DrawUI.tla` を複製して書き換え、一度だけ手で回した確認で、テストには含めていない。

| 変種 | 書き換え | 結果 | 分かること |
|---|---|---|---|
| WF(Timeout) を外す | `Spec` から `/\ WF_vars(Timeout)` を消し、`DrawUI_timeout.cfg` で回す | 反例あり(Commit → Lose → Stuttering) | 合格は「タイマーが実際に発火する」ことに支えられている |
| 応答の喪失をなくす | `Next` から `\/ Lose` を消し、`DrawUI_noTimeout.cfg` で回す | 成立(6 状態) | 付録Bの版が破れる原因は応答の喪失 |

## 実装でも再現したか(Phase 1 の実装で確かめた)

### RLS に渡す role の出どころ【測定】

モデル2の `cache` 設計を実装に置き換えると、P3 の反例が実装でもそのまま再現した。

- 本体の実装では、RLS が使う role と編集権限を、ポリシーの中で DB の `"user"` 表から引く(`db/migrations/002_feature.sql` の `app_role()`・`app_can_edit()`)。アプリが `set_config` で渡すのはユーザーIDだけ
- scratchpad の複製で、role と編集権限を Cookie cache 由来のセッションから `set_config` で渡す形に書き換え(7章で避けた設計)、性質テストを回した
- 結果: **P3 だけが赤**になり、残りの 41 件は緑のままだった

```
FAIL  tests/properties/p3-no-write-after-revoke.test.ts > P3 剥奪後の書き込み禁止: 編集権限を剥奪された後に送られた保存は失敗する(モデル2の反例の手順)
AssertionError: expected { ok: true } to deeply equal { ok: false }
Tests  1 failed | 41 passed (42)
```

テストの手順はモデル2の反例と同じ(読み込む → 編集する → 管理者が剥奪する → 保存を送る)。剥奪後の保存が受理された。
本体の実装では同じテストが緑で、curl で同じ手順を流すと次のようになった。

- 管理者が `update-user` で `canEdit=false` にしたあとも、A市職員の Cookie cache(`session_data`)には `role=a-staff, canEdit=True` が残っていた
- その状態で送った保存は `403 {"ok":false,"reason":"forbidden"}` で拒否された

Better Auth の管理者用エンドポイント(`setRole` など)は、Cookie cache を通らないセッション(`disableCookieCache: true` 相当)で権限を確かめていた(`better-auth` 1.7.22 の `plugins/admin/routes.mjs` の `adminMiddleware`)。
Better Auth 自身も、管理操作では P3 型の問題を避ける設計になっている。こちらで書くエンドポイントも、同じ考え方にそろえた。

### タイムアウトのあとも、サーバーでは保存されていた【測定】

画面の操作で、通信を 15 秒遅らせて保存した(タイムアウトは 10 秒)。
画面は「保存がタイムアウトしました」と出して描画中に戻ったので、L1 は実装でも成り立った。
一方で、DB にはその地物がコミットされていた(保存前 40 件 → 保存後 42 件。1 件は通常の保存、1 件がタイムアウトした保存)。

DrawUI のモデルでは、タイムアウトしたら応答を捨てる、とだけ置いていた。
実装では、リクエストがサーバーに届いていれば、クライアントが待つのをやめても書き込みは起きる。
このままユーザーが保存し直すと、同じ地物が二重にできる。
対策は、保存リクエストに冪等キーを付けて、サーバーで二重の作成を防ぐことだと考える【推測】。
性質にするなら「タイムアウトのあとに保存し直しても、地物は1つしかできない」になる。

→ 2026-11-20 に P10 として goal.md 4章に足し、冪等キーで対処した(下のモデル3の節)。

## モデル3: 実装の状態機械そのものを検査する

2026-11-20 に、アプリ全体を1つの状態機械にした(`src/lib/app/machine.ts`)。
ログイン画面・地図・ポップアップ・描画・保存・ログアウトまで、画面の状態はすべて `State` の1つの値にある。
`next(state, event)` は純粋関数で、通信などの副作用は `Effect` というデータで返す。実行するのは `src/lib/app/effects.ts` だけ。

モデル3は、この `next` を書き直さずにそのまま呼ぶ。モデルとして書いたのは、周りの環境(ユーザーの操作、通信、サーバー)だけ。
DrawUI では、モデル(タイムアウトしたら応答を捨てる)と実装のずれから、タイムアウト後の二重保存を見落とした。
モデル3で出た反例は、そのまま実装の反例になる。

### 環境

- **ユーザー:** どの状態でも、全部の操作を試す(画面では押せないボタンも押す)
  - ログイン(デモユーザー4人。2回まで)、ログアウト
  - 地図をクリック(点は1種類。下書きは4点まで)、ポップアップを閉じる
  - 描画開始(下書きは2つまで)、市を選ぶ、公開にする、確定、取消、再送
- **通信:** 実行層が出した副作用(ログインする/ログアウトする/保存する)には、それぞれちょうど1つの結果が届く。届くのは、画面がどの状態にあるときでもよい
- **サーバー:** 保存の結果は次の4通り。同じキーの保存は、最初の1つだけが残る(DB の一意制約)
  - 保存して、成功が届く
  - 拒否する
  - 保存したが、応答が届かない
  - 要求がサーバーに届かない

「副作用1つにつき結果がちょうど1つ届く」という前提のうち、保存とログインについては実行層のテスト(`src/lib/app/effects.test.ts`)で確かめている。
保存は、応答が来なければタイムアウトで結果不明を返す。4xx は失敗、5xx と通信切れは結果不明を返す。
ログインは、サインインの1回の通信で終わる。サインインが通れば必ずログイン成功を返し、ほかに問い合わせない。
ログアウトは、例外をすべて捕まえて必ず1つのイベントを返す書き方にしてあるが、テストはしていない。

### 性質と結果【測定】

全 73,011 状態で、次の6つがすべて成り立った(1つあたり約1秒)。

| 性質 | 中身 |
|---|---|
| L1 | 保存中なら、その保存の結果はまだ届いていない(届けば保存中を抜ける) |
| P6 | 保存中は、描画開始を押しても新しい描画が始まらない |
| P10 | 結果が分からなくなった保存は、同じキー・同じ中身でしか送り直さない |
| 飛んでいる保存は高々1つ | だから保存の結果に「どの保存の結果か」を書かなくてよい |
| 成功の表示 | 保存できたと表示したら、表示していた図形がそのままサーバーにある |
| 描画の権限 | 編集できない人は描けない。市職員は自分の市にしか描けない |

探索は、ログイン前・ログイン中・ログイン済み(5つの画面)・ログアウト中(3つの画面)のすべてに届いている(対照テストで確認)。

### 検査で見つかったこと【測定】

**1. 保存中にログアウトすると、保存中から抜けられなくなる(L1 違反)**

最初の版では、保存中でもログアウトを押せた。検査器は次の手順を返した。

```
管理者でログインを押す → 管理者のログインが通る → 描画開始(k1)
→ 地図のp1をクリック ×3 → 確定 → ログアウトを押す
→ k1をサーバーが保存し、成功が届く
```

ログアウト中に届いた保存の結果は捨てられる。このあとログアウトが失敗すると、画面は保存中に戻り、もう結果は来ない。
画面を2つのルートに分けていたときは、ログアウトでページごと捨てていたので、この経路はなかった。
1つの状態機械にまとめたことで生まれた経路を、検査器がすぐに見つけた。
保存中・再送中はログアウトを受け付けないようにして直した(ボタンも押せなくした)。

**2. 最初に書いた P10 は強すぎた**

最初は「同じキーで中身の違う保存を一度も送らない」と書いた。検査器は次の経路を反例として返した。

```
確定 → k1をサーバーが拒否する → B市を選ぶ → 確定
```

拒否(4xx)ならサーバーには何も残っていないので、直して送り直しても二重にはならない。これは性質の書き方の誤りだった。
4章の P10 の言葉(タイムアウトのあとに保存し直しても、地物は1つしかできない)どおりに、「結果が分からなくなったキーだけ」を対象にした。
弱めすぎていないことは、次の2つで確かめた。

- 「成功の表示」を強めた。サーバーに何かがあるかではなく、表示していた図形と同じものがあるかを見る
- 対照として「結果不明のあとも図形を直せる」状態機械を渡すと、P10 と「成功の表示」の両方が反例を返す

**3. 保存の結果に付けたキーの照合は要らなかった**

最初は、保存の結果に下書きのキーを付けて、今の下書きと違えば捨てていた。
1を直したあとは、1つのセッションで飛んでいる保存が常に1つだけになった。そのため照合は効いていなかった。
照合を消し、代わりに「飛んでいる保存は高々1つ」を性質として検査に足した。

### 対照(合格が空虚でないことの確認)【測定】

`model/model3-app.test.ts` では、実装の `next` を少しだけ変えた状態機械を2つ渡して、反例が出ることを確かめている。

| 変えたところ | 破れる性質 | 反例の最後の手順 |
|---|---|---|
| 保存中もログアウトできる | L1 | ログアウトを押す → k1をサーバーが保存し、成功が届く |
| 結果不明のあとも図形を直せる | P10、成功の表示 | k1をサーバーが保存したが、応答が届かない → 地図のp1をクリック → 再送 |

サーバー側の冪等キーも、同じように確かめた。
一意制約と `on conflict` を外した素朴な INSERT に戻すと、P10 の性質テスト(`tests/properties/p10-idempotent-create.test.ts`)が `expected 2 to be 1` で赤になった。

### 状態機械にしなかったところ

サーバー(ルートハンドラ、`scopedDb`、RLS)は状態機械にしていない。
リクエストごとに「読む → DB に聞く → 返す」で終わり、画面から見える状態を持たないからだ。
pstack の `principle-model-the-domain` には「分岐も不正な状態も減らさない抽象は疑え」とある。
サーバーを状態機械で包んでも、減る分岐も不正な状態もない。認可の判断は DB(RLS)に置いたままにした。
状態機械に入れたのは、クライアントが知っていることと、サーバーとのやりとり(保存の結果が分からない状態を含む)まで。

## 本物の画面の性質テスト(Bombadil)

`pnpm test:ui 3m`(`tests/ui/`)。Bombadil 0.7.10 が headless の Chrome で画面をランダムに操作し、状態ごとに性質を確かめる。
モデル3が検査するのは `next` までで、`+page.svelte` の配線と、タイルから届く本物の属性は見ていない。ここではそこを見る。

### 環境

- **画面の状態:** `data-app` / `data-screen` / `data-role` / `data-draft-key` / `data-draft-points` で DOM に出している(テスト用の目印)
- **操作:** 地図のランダムな点のクリック、ボタン(確定・描画開始・再送などに重みを付けて、保存まで届きやすくした)、Bombadil の既定のクリック、再読み込み(保存中以外)、待つ
- **サーバー:** `tests/ui/run.ts` が UI テスト用の開発サーバー(5198 番)と、その前にプロキシ(5197 番、`tests/ui/proxy.ts`)を立てる。プロキシは保存API(`POST /api/features`)にだけ障害を起こす。モデル3のサーバーの結果を、本物のサーバーで起こすもの

| 障害 | 割合 | 画面から見えること |
|---|---|---|
| 遅れて成功(0.5〜2秒) | 35% | 保存中が続き、その間にも操作される |
| 保存したが接続が切れる | 15% | ブラウザが自動で送り直す(下の「見つかったこと」) |
| 保存したがゲートウェイが 504 を返す | 15% | 結果不明(サーバーには保存されている) |
| サーバーに届かない(503) | 10% | 結果不明(保存されていない) |
| 拒否する(409) | 15% | 保存失敗 |
| 応答が来ない | 10% | 10秒のタイムアウトで結果不明 |

終わったら DB で、同じ形の地物が二重にできていないかを見る(P10)。名前には時刻が入るので、形で見分ける。キーごとの数は一意制約で必ず1以下になるので、検査にならない。
DB は前後で `restoreSeed` に戻す。

### 空振りしていないことの確認【測定】

プロキシを置く前は、2分の探索で保存中を1回しか観測できず、再送中と結果不明は0回だった。ローカルでは保存が数十ミリ秒で終わるので、このままでは P6・L1 はほとんど何も確かめない。
`run.ts` は、保存中・再送中・結果不明と、ロールごとのポップアップを3回以上観測できなかったら失敗にする。

わざと壊した版(2分ずつ):

| 変異 | 結果 |
|---|---|
| 保存のタイムアウトを外す(`effects.ts`) | L1 が破れた(936状態)。DrawUI の TLC の反例が、本物の画面で再現した |
| 再送で新しいキーを作る(`machine.ts`) | 同じ形の地物が3つ二重にできた(P10) |
| サーバーがクライアントのキーを無視して INSERT する(`authz`) | 同じ形の地物が9つ二重にできた(P10) |
| 保存中もログアウトを押せる(`+page.svelte`) | 「保存中はログアウトできない」が破れた(1,600状態) |
| 保存中も描画ボタンを出し、状態機械も受け付ける(`+page.svelte` と `machine.ts`) | P6 が破れた(49状態) |

P6 は、状態機械だけを壊しても画面からは破れない。保存中のパネルには描画ボタンがなく、描画開始を送る手段がないから。P6 を実際に守っているのはモデル3の検査で、画面の検査は画面側にも抜け道がないことを確かめている。

表の最初の2つは、最初は検出できなかった。直したのは次の2点。

- 探索が保存中に再読み込みすると、状態が初期化されて保存中を抜けてしまう。L1 は「利用者が諦めなくても終わる」ことなので、再読み込みは保存中以外に限った
- 「保存したが接続が切れる」は、ブラウザの自動再送で結果不明にならなかった(次の節)。保存したあとに 504 を返す障害を足した

### 見つかったこと【測定】

**ブラウザは、保存を自分で送り直す。** 使い回した接続が応答なしで切れると、Chrome は同じ POST を1秒以内に自動で送り直した。
最初の計測では、接続を切った7件のうち7件。最終の探索では6件のうち6件。保存の要求は、最初の計測で34件すべて、最終の探索で56件のうち53件が、使い回した接続で届いていた。
画面には何も出ず、利用者は「再送する」を押していない。「再送で新しいキーを作る」変異の探索でも、接続を切った5件のうち5件が同じキーで届いた。この変異では画面の再送は新しいキーになるので、同じキーで送り直したのはブラウザだと分かる。冪等キーがなければ、これだけで地物が二重になる(サーバーがキーを無視する変異では9件)。
P10 は、再送ボタンのためだけの性質ではなかった。

## モデルの限界

- モデル検査が確かめたのは設計(モデル)であって、実装ではない。実装とのずれは、性質ベーステストと E2E で埋める(上のタイムアウトの件が、そのずれの実例)
- モデル2は、ユーザー1人・剥奪1回・保存リクエスト1件まで。複数端末(端末ごとに別の Cookie cache)や、権限の再付与は入れていない
- Cookie cache の更新は「いつ起きてもよい」としている。`maxAge` の具体的な秒数は扱っていない
- P3 は goal.md の定義どおり「剥奪の後に送られた保存」だけを対象にしている。剥奪の前に送られ、剥奪の後に処理された保存は、どちらの設計でも P3 違反にならない
- モデル3は、ログイン2回・下書き2つ・点1種類で4点まで、に絞っている。サーバーの認可(誰がどの市に書けるか)は入れず、「拒否する」という結果だけで表した。認可は性質テスト(P1〜P9)で確かめている
- モデル3は、ログインを1つの副作用として扱っている。実装も、サインインの1回の通信で終わる。Cookie と本人の情報(`role`・`canEdit`)は同じ応答で届く
  - 最初は「サインイン → `/api/me`」の2段だった。2段目だけ失敗すると、Cookie は付いたのに画面は未ログインに戻った。2026-11-20 に1段にした
  - 残るずれは、応答のヘッダーまで届いて本文が途中で切れた場合だけ。このときは Cookie が付いたまま画面は未ログインになる。もう一度ログインすれば新しいセッションになるだけなので、害はない
- UI の性質テストの障害はランダムに選んでいて、Bombadil の `--reproduce` では同じ障害を起こせない。反例が出たら、トレースのスクリーンショットとプロキシの記録から読む
- UI の性質テストでは、ブラウザのコンソールのエラー(`noConsoleErrors`)は見ていない。障害を起こしたときの通信エラーが記録され、中身が `["Fn"]` としか残らないので区別できない
- UI の性質テストでは、ログイン・ログアウトの通信には障害を起こしていない
- 「描画の権限」は、ログインした時点の `canEdit` で判定している。途中で剥奪されても描画ボタンは出たままで、保存はサーバーが拒否する(P3)。画面の性質であって、安全性の性質ではない

## 用語の対応

TLA+ の識別子は ASCII にしたので、対応を書いておく。

| TLA+ | 意味 |
|---|---|
| `Load` / `Edit` / `Send` | 読み込む / 編集する / 保存を送る |
| `Accept` / `Reject` | サーバーが保存を受理する / 拒否する |
| `Revoke` / `RefreshCache` | 管理者が剥奪する / Cookie cache が DB に追いつく |
| `view` / `drawing` / `saving` | 閲覧 / 描画中 / 保存中 |
| `Start` / `AddPoint` / `Commit` / `Cancel` | 描画開始 / 点追加 / 確定 / 取消 |
| `Succeed` / `Fail` / `Lose` / `Timeout` | 保存成功 / 保存失敗 / 応答が失われる / タイムアウト |
