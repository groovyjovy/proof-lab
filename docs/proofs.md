# 形式証明(Lean 4)

最終更新: 2026-11-22(P15 の権限通知と更新の再送を追加)

画面の状態機械と認可の仕様を Lean 4 で書き、性質を証明した。
実装(TypeScript・SQL)が仕様と同じ答えを返すかは、ランダムな入力で突き合わせる(差分テスト)。
仕様で性質を証明し、実装は仕様との一致で確かめる、という分担にした。

## 再現手順

```sh
brew install elan-init           # Lean のバージョン管理(初回だけ)
cd spec && lake build            # 仕様・証明・突き合わせ用の窓口(oracle)を作る。証明が1つでも通らなければ失敗する
pnpm test --project spec         # 実装の状態機械と Lean の仕様を突き合わせる(lake build も自動で走る)
```

Lean は `spec/lean-toolchain` の v4.35.0 を使う(7日ルール。v4.36.0 は 2026-11-16 公開)。Mathlib は使わず、Lean 本体だけで証明した。
`spec/lakefile.toml` で警告をエラーにしているので、`sorry`(書きかけの証明)が残っているとビルドが通らない。わざと `sorry` を入れて、ビルドが失敗することを確かめた。

## 証明した性質

どれも、範囲を区切らずに成り立つ。座標と地物の属性は型の引数にしてあり、状態機械はその中身を見ないので、どんな値でも成り立つ。

### 画面の状態機械(`App`)

到達できる状態は、初期状態から「差し出された操作」「飛んでいる副作用への応答」「地図ライブラリからの知らせ」でたどれるものとして帰納的に定義した(`Reachable`)。知らせは、どの状態でも、いつでも届く。
環境は、飛んでいる副作用の**どれに先に**応答してもよい。だから応答の順序の入れ替わりも含まれる。

飛んでいる副作用は、2つの列に分けて不変条件(`Inv`)を示した。

- 検索のほかの副作用(ログイン・ログアウト・保存・読み込み・更新): 画面の状態だけで決まり、高々1つ
- 範囲の検索: いくつも飛ぶ。番号は送った順に増えていて、どれもまだ振っていない番号より小さい(だから番号が同じなら同じ要求)。応答を待っている検索は、今の本人として飛んでいる

サーバーについての前提は `Server` にまとめた。証明はどんな前提でも成り立ち、性質の中身がこれで決まる。

- `ok a`: 本人 `a` への検索に返してよい結果(P13)。認可の仕様と RLS の突き合わせで「読める地物だけ」と確かめている
- `applied k`: キー `k` の要求が効いて commit された(P14)。環境は、更新に成功を返すのも、変更の知らせにキーを載せるのも、効いたキーについてだけ(`Answers.updated`・`NoticeOk`)。サーバーがこれを守ることは、DB のトリガー(キーに版を書き込んだときにだけ知らせる。PostgreSQL の知らせは commit するまで届かない)と、`tests/properties/p14-change-notice.test.ts` で確かめている

この不変条件を使って、次を証明した。

| 定理 | 性質 | 内容 |
|---|---|---|
| `replies_accepted` | 応答を捨てない | 飛んでいる副作用への応答は、どれも今の状態で受け取れる。前のセッションで送った検索の応答も受け取る。保存中にログアウトできた最初の版は、これが破れていた(L1 の反例) |
| `lane_single_flight` | 検索のほかに飛んでいる副作用は高々1つ | だからその応答には「どの副作用の応答か」を書かなくてよい。検索は同時にいくつも飛ぶので、応答に番号を書く |
| `l1_exit` | L1(状態機械の側) | 応答を待っている副作用(保存・読み込み・更新)の応答を受け取れば、必ず応答待ちを抜ける |
| `receive_only_searches` | 応答で送るのは検索だけ | 応答を受け取って出す副作用は、一覧の読み直し(検索)だけ。保存などを送るのは、利用者の操作だけ |
| `p6` | P6 | 保存中は描画開始を差し出さない(到達できるかに関係なく、どの状態でも) |
| `p10_perform`・`p10_receive`・`p10_notify`・`p10_enter` | P10(状態機械の側) | 結果が分からない下書きは、操作でも応答でも知らせでも変わらない。保存を送るなら、その下書きそのもの |
| `requests_carry_identity` | P11(状態機械の側) | 検索のほかの飛んでいるデータの要求(保存・読み込み・更新)は、どれも画面が今表示している本人として送られている。検索は、前の本人として送ったものも飛んでいる(下の P13) |
| `p4_ops_keep_version` | P4(画面の側) | 編集中の地物と版は、どの操作でも変わらない(変えられるのは名前と備考だけ)。編集の値は読み込みの応答でしか生まれないので、更新に書く版はサーバーから読んだもの |
| `p4_no_update_after_conflict` | P4(画面の側) | 競合したら、読み直すまで更新を送らない(ほかの人の保存を上書きしない) |
| `p12_resend_same`・`p12_unknown_keeps` | P12(画面の側) | 結果が分からない更新は、中身とキーを持ったままにし、送り直すときは同じ中身・同じキーで送る |
| `offer_depends_on_kind_only` | 押せるかは状態だけで決まる | 差し出すかどうかは操作の中身(座標・キー・市)によらない。画面はこれを前提に、状態からボタンの押せる・押せないを決めている |
| `p13_only_latest` | P13 古い応答で一覧を替えない | 検索の応答で状態が変わるなら、それは今の本人が送った、いちばん新しい検索への応答。追い越された検索や、前のセッションの検索の応答は何も変えない。前の本人の検索への「本人が変わった」でも、今の本人はログアウトしない |
| `p13_shown_ok` | P13 一覧は今の本人のもの | サーバーが本人 `a` への検索に `ok a` を満たす結果しか返さないなら、一覧はいつも `ok 今の本人` を満たす(`ok` は何でもよい)。`ok a` を「`a` が読める地物」とし、認可の仕様(`Authz.canRead`)と RLS の突き合わせと合わせると、ログインし直した前の本人(管理者)への応答が届いても、今の本人(閲覧者)の一覧には出ない |
| `p13_settled` | P13 検索中でなければ今の範囲 | 検索中でなければ、一覧は今見えている範囲のもの |
| `p13_pending_inflight` | P13 検索中は抜けられる | 検索中なら、その検索は今の本人として飛んでいる。応答はどれも受け取れるので、届けば検索中を抜ける |
| `notice_keeps_busy` | 知らせで応答待ちを抜けない | どの知らせでも、応答待ち(保存中・読込中・更新中)を抜けない。抜けると、飛んでいる副作用の応答を受け取れなくなる |
| `p14_other_stream_ignored` | P14 前の本人の流れを捨てる | ログインし直す前に開いた変更の流れから届いた知らせは、何も変えない |
| `p14_stale_only_newer` | P14 警告が正直 | 「ほかの人が更新した」と出すのは、今の本人の流れから、編集している地物が読み込んだときより新しい版になったと知らされたときだけ。自分の更新が戻ってきた知らせは、読み込んだ版と同じなので出さない |
| `p14_unknown_resolved_applied` | P14 知らせで成功にするのは効いたときだけ | 結果が分からない更新を、知らせで成功(閲覧)にするのは、そのキーが効いたときだけ(サーバーが効いたキーしか知らせない、という前提 `NoticeOk` のもとで) |
| `p14_update_success_applied` | P14 応答で成功にするのも効いたときだけ | 更新中(送り直しを含む)に応答で成功にするのは、成功の応答か、効いたという知らせを先に受けたうえでの結果不明の応答のどちらかで、どちらもそのキーが効いている |
| `p15_commit_permitted` | P15 確定は送るときの権限で | 確定で保存を送るのは、送るときの本人がその下書きを描けるときだけ(編集権限があり、管理者か担当の市)。ログインの途中で権限が変わると下書きは残るので、事例研究3までの「下書きがあるのは編集できる人だけ」(`draft_permission`)は成り立たなくなり、この定理に言い直した |
| `p15_save_edit_permitted` | P15 編集の保存も送るときの権限で | 編集の保存で更新を送るのは、送るときの本人がその地物を編集できるときだけ。結果が分からない要求の再送は含めない(同じ要求の送り直しで、サーバーが今の権限で判断する) |
| `p15_selected_readable` | P15 ポップアップは読める地物だけ | ポップアップの地物は、今の本人が読めるもの。地図で選ぶときに今の権限で確かめ、権限が変わったら外す |
| `p15_listing_since` | P15 一覧は今の権限での検索だけ | 一覧は、今の権限になってから送った検索の結果だけ。知らされる前に送った検索の応答は、届いても出さない |
| `p15_change_applied` | P15 権限の知らせで差し替える | 今の本人の権限が変わったと知らされたら(今と違う権限なら)、本人を差し替え、選んでいた地物と一覧を消す |
| `p15_other_user_ignored` | P15 別人の権限の知らせは捨てる | 本人の ID が違う権限の知らせは、何も変えない |
| `p15_same_permission_ignored` | P15 同じ権限の知らせは何もしない | 今と同じ権限の知らせ(変更の流れをつなぐたびにサーバーが送る)では、選んでいる地物や一覧を消さない |
| `p15_resend_rejected_unknown` | P15 送り直しの拒否は結果不明のまま | 結果が分からない更新の送り直しが拒否されても、結果不明のまま。権限を外されたあとは効いたキーの送り直しもサーバーが拒否する(測った)ので、拒否は「効かなかった」ことを意味しない |

検索の番号は、タブの中で一度きりにした(ログインし直しても振り直さない)。番号をセッションの中に持つと、
ログインし直した直後の番号が、前の本人の検索の番号と重なる。`p13_shown_ok` は、この作りでは証明できない
(モデル3の対照で、管理者への応答が閲覧者の一覧に出る反例が出る)。

L1 は活性(いつか必ず終わる)なので、状態機械だけでは言い切れない。
`replies_accepted` と `l1_exit` で「応答が届けば必ず抜ける」までを証明し、「副作用はいつか必ず応答する」は `src/lib/app/effects.ts` のタイムアウトに任せた。後者はテスト(`effects.test.ts`)と、TLA+ のモデル(公平性の仮定つき)で確かめている。

### 認可(`Authz`)

| 定理 | 性質 | 内容 |
|---|---|---|
| `p1` | P1 地域分離 | 市職員が読める地物は、担当の市のものだけ |
| `p2` | P2 属性秘匿 | 閲覧者には `owner_name` を返さない |
| `p7` | P7 公開範囲 | 閲覧者が読める地物は、公開の地物だけ |
| `p8_needs_permission`・`p8_own_city`・`p8_no_move` | P8 書き込みの地域分離 | 書き込めるのは編集権限がある人だけ。市職員は担当の市にしか書き込めず、他市へ移せない |
| `p3_db` | P3 剥奪後の書き込み禁止 | 保存を DB の編集権限で認可するなら、剥奪のあとの保存は、Cookie cache がいつ更新されても拒否される |
| `p3_cache_counterexample` | P3 の反例 | Cookie cache の値で認可すると、剥奪の直後の保存が通る(モデル2・TLA+ と同じ反例) |
| `p4_second_rejected`・`p4_kept` | P4 ロストアップデートなし | 同じ版を読んだ二人のうち、先の人の更新が効いたら、別のキーで送った後の人の更新は競合になる。効いた更新は、それまでの編集を消さない |
| `p12_replay` | P12 更新の冪等性 | 一度効いたキーの更新は、版や中身が何であっても、もう効かない(成功だけを返す)。結果が分からない更新を送り直しても、自分の更新と競合しない |
| `p10_server` | P10(サーバーの側) | 同じキーで何度作成しても、キーごとに行は1つ |
| `p11` | P11(サーバーの側) | サーバーが答えるのは、要求に書いた本人とセッションの本人が同じときだけ。状態機械の側(`requests_carry_identity`、タイルの URL の `as`)と合わせて、画面に出る応答は表示している本人として認可されたもの |

認可の判断は「誰が」「どの地物を」だけで決まり、地物1件ずつに同じ判断をする。だから件数や出口によらない。

### 仕様から SQL を書き出す

読める・書き込める・`owner_name` が見える、の3つの判断は、Lean の中で条件の式(`Cond`)として書いた。
同じ式を、Lean では評価して性質を証明し(`Cond.eval`)、PostgreSQL へは関数として書き出す(`Cond.sql`)。
`db/migrations/002_feature.sql` の `app_can_read`・`app_can_write`・`app_sees_owner` は、この書き出したもの(`pnpm spec:sql`)。手で書き換えると `tests/conformance/sql.test.ts` が落ちる(わざと書き換えて確かめた)【測定】。
式を変えて性質が崩れれば証明が通らず、書き出しを忘れればテストが落ちる。書き出す処理(`Cond.sql`)そのものは証明していないので、PostgreSQL が仕様と同じ判断をすることは、判断表の全行で突き合わせて確かめている。

3つの関数は、どれも行の `city` と `public` を引数に取る形にそろえた。式が引数にない列を使えば、マイグレーションが SQL のエラーで止まる。利用者が決まらない(`app_role()` が null の)ときは、どれも false になる。

### 公理【測定】

性質を表す45個の定理(画面32・認可とサーバー13)のどれも、Lean の標準の公理(`propext`・`Quot.sound`・`Classical.choice`)だけに依存している。`sorryAx`(書きかけの証明)や `Lean.ofReduceBool`(`native_decide`)には依存していない【測定】。
`tests/conformance/axioms.test.ts` が毎回 `#print axioms`(`spec/Axioms.lean`)の出力を読んで確かめる。確かめる定理がこのページの表と同じかも見るので、表に足した定理を確かめ忘れることはない(前は手で確かめていた)。

## 実装との突き合わせ(差分テスト)

証明したのは仕様で、実装ではない。実装が仕様と同じ答えを返すことを、ランダムな入力で確かめる。
AWS の認可言語 Cedar と同じ考え方にした。Cedar は Lean で書いた実行できるモデルで性質を証明し、本番の Rust の実装がモデルと同じ答えを返すかを差分テストで確かめている(Disselkoen ほか, "How We Built Cedar: A Verification-Guided Approach", FSE Companion 2024, [arXiv:2407.01688](https://arxiv.org/abs/2407.01688))。

- 画面の状態機械: 初期状態(未ログインか、ログイン済みの本人)から、操作と応答のランダムな列を流す。1つずつの結果(状態・副作用・差し出す操作の一覧)が、TypeScript と Lean で一致するかを見る。差し出していない操作・受け取れない応答は、両方とも「なし」になるはず
- 2,000 列を流して一致した。到達できる画面の状態をすべて通ったことも確かめている(空振りの確認)【測定】
- `pnpm test` では決まった種で流す(`tests/seed.ts`)。何度流しても同じ 2,000 列で、生成した列のハッシュが一致することを確かめた【測定】。決まった種なので、空振りの確認も運で落ちない。落ちたら、生成器がその場面に届かなくなった、という確かな知らせになる。新しい種で流すのは `pnpm explore`(届かなかった場面は報告だけにする)
- 範囲内の網羅(`tests/conformance/exhaustive.test.ts`): モデル3の4範囲がたどる画面の状態(重複なしで 7,183)のすべてに、すべての種類の操作・応答・知らせ(68種類)を1つずつ当て、488,444 通りで結果が一致した【測定】(権限の変更を足す前は 2,075 状態 × 59 種類 = 122,425 通り、地物の変更の知らせを足す前は 1,387 状態 × 52 種類 = 72,124 通り、検索を足す前は 949 状態 × 35 種類 = 33,215 通り、編集を足す前は 671 状態 × 30 種類 = 20,130 通り)。この文の数は、テストが今の数と同じかを確かめる(書き忘れると落ちる)。検索の応答は、番号 0〜4 と結果3種類の組をすべて当てる。ランダムな列は「たまたま通った経路」しか見ないが、こちらはモデル3の範囲の中で漏れがない。わざと壊した版(ポップアップがなくても閉じるを差し出す、2点で確定できる)は、どちらも不一致になった
- わざと壊した版(どちらも反例が出た)【測定】:
  - 保存中も「取消」を差し出す
  - 2点で確定できる

- 認可: Lean の仕様から、利用者(ロール4つ × 編集権限の有無)と地物(市 × 公開)のすべての組み合わせの判断表(32行)を引く。性質テスト(`tests/properties/`)は、この表を期待値にして、本物の PostgreSQL(RLS)の答えと突き合わせる。テストの中で認可の判断を書き直さない(前は `rules.ts` に手で書いていた)
  - 全範囲を取ったとき、どの出口(一覧・範囲検索・タイル)からも、仕様が読めるとする地物がちょうど届き、`owner_name` の出し方も仕様どおり(`exits-control.test.ts`)
  - ランダムな範囲・ロールの組で、仕様が読めないとする地物が届かない(P1・P5・P7)、`owner_name` の出し方が仕様どおり(P2)、書き込みの可否が仕様どおり(P8・P10)
  - 判断表の全行(`authz-conformance.test.ts`): 判断の入力は有限(ロール4 × 編集権限2 × 市2 × 公開2 = 32行)なので、ランダムではなく全部を試す。行ごとに地物を1つ入れ、読む・作る・市を移して編集するの結果を仕様と比べる(移す先の市2つで64通り)。シードの編集権限だけでなく、権限を外した場合も試す。64通りとも一致した【測定】。RLS を「編集権限を見ない」に変えた版では、64通りのうち16通りが不一致になった【測定】
  - RLS を「市職員に他市の公開の地物も読ませる」に変えた版では、性質テスト9件が不一致になった【測定】

## 証明で見つかったこと

- ログイン中に権限が変わると、`DraftOk` は成り立たない。下書きがあっても権限は取り消せるため、描画中の入力を残し、確定で保存を送る時点の権限を証明する形にした。描画の判断も `Authz.canCreate` に揃えた。閲覧者に編集権限だけを与えたときにも、画面と RLS の判断が一致する
- `Server.ok` は本人の ID で結果を許す述語なので、同じ ID の権限が変わる環境の前提には使えない。`p15_listing_since` は直近の権限通知後に送った検索だけが一覧に出ることを示す。通知がなければ画面の権限が古いままになる反例はモデル3で出た
- `Answers` は、すでに効いたキーに「拒否」を返すことも許していた。剥奪後にこの応答が実際に起きると、拒否を「更新失敗」と表示する版はモデル3で10手の反例になった。再送拒否で結果不明に戻ることを `p15_resend_rejected_unknown` で証明した

- 変更の知らせ(2026-11-22)では、「自分のキーの知らせが届いたら、結果不明の更新を成功にしてよい」が、そのままでは証明できなかった。環境はどんな知らせでも送れるので、効いていないキーの知らせも届きうる。証明に要る前提(サーバーは効いたキーしか知らせない、`NoticeOk`)を書き出すと、それがそのままサーバーの作りの要求になった。知らせはキーを取ったとき(版 -1)ではなく、版を書き込んだとき(効いたとき)に出し、commit するまで届けない。この要求は性質テストで確かめ、知らせる時点をずらした版(キーを取っただけで知らせる)が赤になることも確かめた
- 更新中に自分のキーの知らせが届いたとき、応答を待たずに成功にすると、不変条件(検索のほかに飛んでいる副作用は、画面の状態だけで決まる)が崩れる。飛んでいる更新の応答を受け取れなくなるからだ。そこで「効いた」と覚えるだけにし(`updating` の `applied`)、応答が結果不明でも成功にできるようにした。P11 のタイルの知らせ(保存中に画面を閉じない)と同じ形の制約を、証明がもう一度課した

- 範囲の一覧(2026-11-21)では、「飛んでいる副作用は高々1つ」という前提が崩れた。この前提は、応答に「どの副作用の応答か」を書かずに済ませる根拠で、P11 の定理(飛んでいる要求はどれも今の本人として送られている)も黙って使っていた。検索を足すと、前の本人として送った検索がまだ飛んでいるので、P11 の定理はそのままでは偽になった。証明が通らないことで、どの定理がこの前提に寄りかかっていたかが分かった。不変条件を「検索のほか(高々1つ)」と「検索(番号で区別)」の2つの列に分け、P11 の定理は検索のほかの列について述べ直した
- 検索の「本人が変わった」(412)を、保存などの「本人が変わった」と同じ応答にすると、前の本人の検索への 412 で今の本人がログアウトし、待っていた保存の応答も捨てることになる。応答に番号を付けて、いちばん新しい検索への 412 だけを信じるようにした

- 既存の地物の編集(2026-11-21)では、仕様を先に書き、証明を先に通してから TypeScript を書いた。応答待ちの状態(保存中・読込中・更新中)を `isBusy` にまとめると、不変条件・応答を捨てない・L1 の証明は、場合分けが増えただけで、ほとんどそのまま通った。新しく要ったのは、編集の値と版が操作で変わらないこと(P4)と、結果不明の更新の再送が同じキーであること(P12)の定理だけだった

- P11 の知らせ(地図のタイルが本人違いで断られた)を、最初は「どの状態でもログイン画面に戻す」つもりだった。保存中にそうすると、飛んでいる保存の応答が、もう受け取れない状態に届く。不変条件(飛んでいる副作用は画面の状態だけで決まる)の証明がこれを許さない。保存中・ログアウト中は何もせず、保存の要求にも本人を書いてあるので、本人違いは保存の応答(`本人が変わった`)で分かるようにした。モデル3でも、保存中に知らせで画面を閉じる版を渡すと「応答を捨てない」が破れる

- P10 の定理を最初は「結果が分からない下書きから出る副作用は、その下書きの保存だけ」と書いた。証明が通らず、反例を見ると、結果不明の画面でログアウトするとログアウトの副作用が出る。性質として欲しいのは「保存を送るなら、その下書きそのもの」なので、そう書き直した。仕様の書き間違いを、証明が止めた例

## 証明していないもの

- DB と画面の権限が、通知の配信が落ち着くと一致すること。モデル3の橋の性質と、接続時・ロール変更時・編集権限変更時の配信を確かめるサーバーテストが扱う
- 可変な DB の更新結果を参照した「失敗と表示した更新は効いていない」という性質。`Sys` は DB の権限と効いたキーの履歴を持たないので、モデル3の編集の範囲で確かめている
- 条件の式を SQL に書き出す処理(`Cond.sql`)。書き出した SQL が仕様と同じ判断をすることは、判断表の全行で突き合わせている。RLS の残りの部分(ポリシーをどの操作に付けるか、ビューが RLS を通すか)は手で書いていて、性質テストで確かめている
- 画面(Svelte)の描画。押せるかどうかは、`#lib/ui` の部品が状態機械の差し出す操作から決める作りにして、lint で強制した。正しく描けているかは UI の性質テスト(Bombadil)で確かめる
- 副作用がいつか必ず応答すること(上の L1)
- 地図ライブラリ(MapLibre)が自分で取りに行くタイルの通信。状態機械の外にある。タイルの URL に本人(`as`)を書くのは状態機械の状態から作るが、その通信そのものはモデルに入っていない(`docs/screens.md` の「画面とサーバーで本人がずれる」)
