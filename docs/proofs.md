# 形式証明(Lean 4)

最終更新: 2026-11-21(P11 を足した)

画面の状態機械と認可の仕様を Lean 4 で書き、性質を証明した。
実装(TypeScript・SQL)が仕様と同じ答えを返すかは、ランダムな入力で突き合わせる(差分テスト)。
仕様で性質を証明し、実装は仕様との一致で確かめる、という分担にした。

## 再現手順

```sh
brew install elan-init           # Lean のバージョン管理(初回だけ)
cd spec && lake build            # 仕様・証明・突き合わせ用の窓口(oracle)を作る。証明が1つでも通らなければ失敗する
pnpm test --project spec         # 実装の状態機械と Lean の仕様を突き合わせる(lake build も自動で走る)
```

Lean は `spec/lean-toolchain` の v4.35.0 を使う(7日ルール。v4.36.0 は 2026-11-16 公開)。Mathlib は使わず、Lean 本体だけで証明した。
`spec/lakefile.toml` で警告をエラーにしているので、`sorry`(書きかけの証明)が残っているとビルドが通らない。わざと `sorry` を入れて、ビルドが失敗することを確かめた。

## 証明した性質

どれも、範囲を区切らずに成り立つ。座標と地物の属性は型の引数にしてあり、状態機械はその中身を見ないので、どんな値でも成り立つ。

### 画面の状態機械(`App`)

到達できる状態は、初期状態から「差し出された操作」「飛んでいる副作用への応答」「地図ライブラリからの知らせ」でたどれるものとして帰納的に定義した(`Reachable`)。知らせは、どの状態でも、いつでも届く。
飛んでいる副作用が画面の状態だけで決まる、という不変条件(`Inv`)を示し、それを使って次を証明した。

| 定理 | 性質 | 内容 |
|---|---|---|
| `replies_accepted` | 応答を捨てない | 飛んでいる副作用への応答は、どれも今の状態で受け取れる。保存中にログアウトできた最初の版は、これが破れていた(L1 の反例) |
| `single_flight` | 飛んでいる副作用は高々1つ | だから応答に「どの副作用の応答か」を書かなくてよい |
| `draft_permission` | 描画の権限 | 下書きがあるのは編集できる人だけ。管理者以外の下書きは自分の市 |
| `p6` | P6 | 保存中は描画開始を差し出さない(到達できるかに関係なく、どの状態でも) |
| `l1_exit` | L1(状態機械の側) | 保存中に保存の応答を受け取れば、必ず保存中を抜ける |
| `p10_perform`・`p10_receive`・`p10_notify`・`p10_enter` | P10(状態機械の側) | 結果が分からない下書きは、操作でも応答でも知らせでも変わらない。保存を送るなら、その下書きそのもの |
| `requests_carry_identity` | P11(状態機械の側) | 飛んでいる保存は、どれも画面が今表示している本人として送られている |
| `offer_depends_on_kind_only` | 押せるかは状態だけで決まる | 差し出すかどうかは操作の中身(座標・キー・市)によらない。画面はこれを前提に、状態からボタンの押せる・押せないを決めている |

L1 は活性(いつか必ず終わる)なので、状態機械だけでは言い切れない。
`replies_accepted` と `l1_exit` で「応答が届けば必ず抜ける」までを証明し、「副作用はいつか必ず応答する」は `src/lib/app/effects.ts` のタイムアウトに任せた。後者はテスト(`effects.test.ts`)と、TLA+ のモデル(公平性の仮定つき)で確かめている。

### 認可(`Authz`)

| 定理 | 性質 | 内容 |
|---|---|---|
| `p1` | P1 地域分離 | 市職員が読める地物は、担当の市のものだけ |
| `p2` | P2 属性秘匿 | 閲覧者には `owner_name` を返さない |
| `p7` | P7 公開範囲 | 閲覧者が読める地物は、公開の地物だけ |
| `p8_needs_permission`・`p8_own_city`・`p8_no_move` | P8 書き込みの地域分離 | 書き込めるのは編集権限がある人だけ。市職員は担当の市にしか書き込めず、他市へ移せない |
| `p3_db` | P3 剥奪後の書き込み禁止 | 保存を DB の編集権限で認可するなら、剥奪のあとの保存は、Cookie cache がいつ更新されても拒否される |
| `p3_cache_counterexample` | P3 の反例 | Cookie cache の値で認可すると、剥奪の直後の保存が通る(モデル2・TLA+ と同じ反例) |
| `p4_second_rejected`・`p4_kept` | P4 ロストアップデートなし | 同じ版を読んだ二人のうち、後の保存は通らない。通った保存は、それまでの編集を消さない |
| `p10_server` | P10(サーバーの側) | 同じキーで何度作成しても、キーごとに行は1つ |
| `p11` | P11(サーバーの側) | サーバーが答えるのは、要求に書いた本人とセッションの本人が同じときだけ。状態機械の側(`requests_carry_identity`、タイルの URL の `as`)と合わせて、画面に出る応答は表示している本人として認可されたもの |

認可の判断は「誰が」「どの地物を」だけで決まり、地物1件ずつに同じ判断をする。だから件数や出口によらない。

### 公理【測定】

`#print axioms` で、23個のどの定理も Lean の標準の公理(`propext`・`Quot.sound`・`Classical.choice`)だけに依存し、`sorryAx`(書きかけの証明)に依存していないことを確かめた(2026-11-21)。

## 実装との突き合わせ(差分テスト)

証明したのは仕様で、実装ではない。実装が仕様と同じ答えを返すことを、ランダムな入力で確かめる。
AWS の認可言語 Cedar と同じ考え方にした。Cedar は Lean で書いた実行できるモデルで性質を証明し、本番の Rust の実装がモデルと同じ答えを返すかを差分テストで確かめている(Disselkoen ほか, "How We Built Cedar: A Verification-Guided Approach", FSE Companion 2024, [arXiv:2407.01688](https://arxiv.org/abs/2407.01688))。

- 画面の状態機械: 初期状態(未ログインか、ログイン済みの本人)から、操作と応答のランダムな列を流す。1つずつの結果(状態・副作用・差し出す操作の一覧)が、TypeScript と Lean で一致するかを見る。差し出していない操作・受け取れない応答は、両方とも「なし」になるはず
- 2,000 列を流して一致した。到達できる画面の状態をすべて通ったことも確かめている(空振りの確認)【測定】
- 範囲内の網羅(`tests/conformance/exhaustive.test.ts`): モデル3がたどる画面の状態(重複なしで 671)のすべてに、すべての種類の操作・応答・知らせ(30種類)を1つずつ当て、20,130 通りで結果が一致した【測定】。ランダムな列は「たまたま通った経路」しか見ないが、こちらはモデル3の範囲の中で漏れがない。わざと壊した版(ポップアップがなくても閉じるを差し出す、2点で確定できる)は、どちらも不一致になった
- わざと壊した版(どちらも反例が出た)【測定】:
  - 保存中も「取消」を差し出す
  - 2点で確定できる

- 認可: Lean の仕様から、利用者(ロール4つ × 編集権限の有無)と地物(市 × 公開)のすべての組み合わせの判断表(32行)を引く。性質テスト(`tests/properties/`)は、この表を期待値にして、本物の PostgreSQL(RLS)の答えと突き合わせる。テストの中で認可の判断を書き直さない(前は `rules.ts` に手で書いていた)
  - 全範囲を取ったとき、どの出口(一覧・範囲検索・タイル)からも、仕様が読めるとする地物がちょうど届き、`owner_name` の出し方も仕様どおり(`exits-control.test.ts`)
  - ランダムな範囲・ロールの組で、仕様が読めないとする地物が届かない(P1・P5・P7)、`owner_name` の出し方が仕様どおり(P2)、書き込みの可否が仕様どおり(P8・P10)
  - 判断表の全行(`authz-conformance.test.ts`): 判断の入力は有限(ロール4 × 編集権限2 × 市2 × 公開2 = 32行)なので、ランダムではなく全部を試す。行ごとに地物を1つ入れ、読む・作る・市を移して編集するの結果を仕様と比べる(移す先の市2つで64通り)。シードの編集権限だけでなく、権限を外した場合も試す。64通りとも一致した【測定】。RLS を「編集権限を見ない」に変えた版では、64通りのうち16通りが不一致になった【測定】
  - RLS を「市職員に他市の公開の地物も読ませる」に変えた版では、性質テスト9件が不一致になった【測定】

## 証明で見つかったこと

- P11 の知らせ(地図のタイルが本人違いで断られた)を、最初は「どの状態でもログイン画面に戻す」つもりだった。保存中にそうすると、飛んでいる保存の応答が、もう受け取れない状態に届く。不変条件(飛んでいる副作用は画面の状態だけで決まる)の証明がこれを許さない。保存中・ログアウト中は何もせず、保存の要求にも本人を書いてあるので、本人違いは保存の応答(`本人が変わった`)で分かるようにした。モデル3でも、保存中に知らせで画面を閉じる版を渡すと「応答を捨てない」が破れる

- P10 の定理を最初は「結果が分からない下書きから出る副作用は、その下書きの保存だけ」と書いた。証明が通らず、反例を見ると、結果不明の画面でログアウトするとログアウトの副作用が出る。性質として欲しいのは「保存を送るなら、その下書きそのもの」なので、そう書き直した。仕様の書き間違いを、証明が止めた例

## 証明していないもの

- SQL(RLS)そのもの。仕様と同じ判断をすることは、判断表の全行で突き合わせている
- 画面(Svelte)の描画。押せるかどうかは、`#lib/ui` の部品が状態機械の差し出す操作から決める作りにして、lint で強制した。正しく描けているかは UI の性質テスト(Bombadil)で確かめる
- 副作用がいつか必ず応答すること(上の L1)
- 地図ライブラリ(MapLibre)が自分で取りに行くタイルの通信。状態機械の外にある。タイルの URL に本人(`as`)を書くのは状態機械の状態から作るが、その通信そのものはモデルに入っていない(`docs/screens.md` の「画面とサーバーで本人がずれる」)
